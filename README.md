# .github

Org共通のIssueテンプレート・PRテンプレート・運用ルールを管理するリポジトリです。

## 基盤改善プロジェクト管理方針

クライアント・サーバー・インフラの基盤改善を、GitHub Issue + Projectで一元管理する。

- **コードとの一体管理**: Notionのチケット管理ではなく、リポジトリやコードに近い場所で管理することで、IssueとPR・コードの紐づけを自然に保ち、改修の背景から実装までを一気通貫で追跡できる状態とする
- **知見の蓄積**: 調査の過程や技術的な知見をIssueに記録し、将来同様の課題に直面した際や新メンバーのオンボーディング時に参照できる資産とする
- **意思決定の構造化**: 決定事項・背景・却下した選択肢をIssueに残すことで、口頭やチャットでの決定の散逸を防ぎ、AIによるコンテキスト参照にも適した構造とする
- **進捗の可視化**: 親Issueで改善テーマとゴールを定義し、Sub-Issueで具体タスクに分解することで、テーマ単位の進捗を把握できるようにする

## 管理ツールの使い分け

| 種別 | 管理場所 | 備考 |
|------|----------|------|
| バグ | GitHub Issue + Projects | 🐛 バグ報告テンプレートを使用 |
| 基盤改善 | GitHub Issue + Projects | 🔧 基盤改善テンプレートを使用 |
| 機能開発 | Notion | 既存のチケット運用を継続 |

機能開発の中で基盤的な作業が発生した場合は、GitHub Issueを起票してNotionチケットからリンクする。

## Issueの構造

```
親Issue（改善テーマ / バグの大枠）
├── Sub-Issue（具体タスク①）
├── Sub-Issue（具体タスク②）
└── Sub-Issue（具体タスク③）
```

- **親Issue**: テーマ・ゴール・背景を記載。調査メモや意思決定はコメントに追記していく
- **Sub-Issue**: PRと紐づく作業単位。完了条件を明確にする

## 意思決定の記録フォーマット

Issueのコメントに以下の形式で追記する。

```markdown
## 決定: 〇〇とする
- 背景: ...
- 比較した選択肢: A案 / B案
- 採用理由: ...
- 却下理由: ...
```

## コミット・PRのルール

- コミットメッセージにIssue番号を含める（`refs #1234` / `closes #1234`）
- PRはテンプレートに沿って、関連Issue・変更概要・テスト方法を記載する
